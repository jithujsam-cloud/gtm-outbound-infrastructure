PHASE 1 — ICP PROMPT ARCHITECTURE
==================================================

Goal:
Create a proper two-layer prompt architecture.

SYSTEM PROMPT:
The system prompt defines HOW the validation engine behaves.

It must be stable and reusable across projects.

It should establish that the model is an ICP classification engine and must:
- Evaluate every supplied lead against the user's ICP criteria.
- Follow the user's ICP criteria exactly.
- Not invent additional ICP requirements.
- Use company information as the primary evidence.
- Use available company name, industry, domain, description, title and other supplied fields as evidence.
- Never invent a lead ID.
- Never modify a supplied lead ID.
- Never omit a supplied lead.
- Return exactly one classification per supplied lead.
- Set vertical_match to true only when the lead clearly matches the user's defined ICP.
- Set matched_vertical to the matching ICP category when there is one.
- Set matched_vertical to null when there is no match.
- Provide concise reasoning based on available evidence.
- Follow the structured response schema exactly.
- Never return prose outside the required structured output.

Do NOT put project-specific ICP criteria in the system prompt.

USER PROMPT:
The user prompt contains the project-specific ICP logic.

It should contain clearly separated sections:
ICP CRITERIA
TARGET INDUSTRIES
COMPANY CHARACTERISTICS
GEOGRAPHY
COMPANY SIZE
POSITIVE SIGNALS
NEGATIVE SIGNALS
DECISION RULE
UNCERTAINTY RULE

Then:
LEADS TO CLASSIFY

Each lead should contain only the fields necessary for classification.

Example structure:
Lead ID:
Name:
Company:
Industry:
Domain:
Position:
Other relevant company information:

The user's ICP instructions must be sent ONCE per batch, not repeated inside every lead.

The request structure should conceptually be:

SYSTEM:
[stable validation system prompt]

USER:
[ICP criteria]
+
[Lead 1]
[Lead 2]
[Lead 3]

NOT:
Lead 1 + full ICP prompt
Lead 2 + full ICP prompt
Lead 3 + full ICP prompt

This is important for reducing input-token usage.

Preserve the existing structured output contract:
lead_id
vertical_match
matched_vertical
reasoning

For batch requests, retain the object-root schema required by OpenAI strict structured output:
{
  "results": [
    {
      "lead_id": "...",
      "vertical_match": true,
      "matched_vertical": "...",
      "reasoning": "..."
    }
  ]
}

Do not break the existing single-lead path.
Do not change provider selection behavior.

Create a clean implementation so the system prompt and user prompt can be changed independently later.

If the existing database already stores the user's ICP prompt/template, reuse it rather than creating duplicate storage.

If the current data model is insufficient to distinguish system prompt from user ICP prompt, propose the smallest database change required.

Do not add unnecessary UI yet.

PHASE 2 — LLM USAGE, COST AND VALIDATION RUN TRACKING
==================================================

Goal:
Make every validation run measurable.

We need to know exactly what happened during every ICP validation run.

For every LLM API request, capture where the provider actually returns the information:
- provider
- model
- request ID if available
- operation
- timestamp
- duration
- status
- attempt
- number of leads in request
- input tokens
- cached input tokens if available
- output tokens
- total tokens if available
- calculated input cost
- calculated cached-input cost
- calculated output cost
- calculated total cost
- raw provider error if failed

For GPT-4.1-mini use the current official API pricing configured in the application rather than hardcoding estimates in the UI.

Cost calculation must use actual usage returned by the API.

Conceptually:
input_cost = non_cached_input_tokens * input_price / 1,000,000
cached_input_cost = cached_input_tokens * cached_input_price / 1,000,000
output_cost = output_tokens * output_price / 1,000,000
total_cost = input_cost + cached_input_cost + output_cost

Do not estimate tokens based on character count.
Do not calculate cost from number of leads.
Use actual provider usage whenever available.

IMPORTANT:
Do not store API keys in these records.

VALIDATION RUN LEVEL:

A validation job should have enough aggregated information to answer:
- How many leads were requested?
- How many were processed?
- How many succeeded?
- How many failed?
- How many matched?
- How many did not match?
- How many API requests were made?
- Total input tokens?
- Total cached input tokens?
- Total output tokens?
- Total tokens?
- Total cost?
- Average cost per successfully processed lead?
- Total duration?
- Average request duration?
- Success rate?
- Failure rate?
- Model used?
- Provider used?

Do not duplicate data unnecessarily if it can be derived safely from existing records.
Prefer storing request-level facts and deriving cumulative statistics from them.

The existing api_operation_logs should remain useful for low-level debugging.

The validation job should become the higher-level "run".

Relationship:
Validation Run
  API Request 1
  API Request 2
  API Request 3
  API Request 4

Each API request may contain multiple leads.

The UI must therefore NOT assume:
1 API log = 1 lead.

Add the smallest appropriate database changes through a new migration.

Respect the existing manual Supabase SQL Editor migration workflow.

Migration must be safe and compatible with the existing project.
Do not use CREATE INDEX CONCURRENTLY.
Do not modify existing production data destructively.
Preserve RLS/security behavior.

If provider usage data is unavailable for a failed request, store null rather than inventing values.

For OpenAI, capture the actual usage object returned by the API.

Keep raw provider response/error data separate from calculated metrics.

Do not store unnecessary sensitive information.
